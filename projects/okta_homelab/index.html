Okta Identity Platform for the Home Lab

Single sign on, group based access, the org managed as code, and a read only AI assistant

Okta is the identity provider for my home lab. Cloudflare Access, Immich and Forgejo sign people in through it over OpenID Connect. Access follows group membership, one policy enforces MFA for all three, and the org is managed as code. An AI assistant can read the org and cannot change it.

Architecture

The lab is two machines, a Mac mini and a Windows PC. Its services reach the internet through a Cloudflare Tunnel, so the router has no inbound ports open. Four hostnames sit behind Cloudflare Access: a dashboard, a file browser, Forgejo for Git and Immich for photos. In Okta, Cloudflare Access, Immich and Forgejo are each an OIDC web app that uses the authorization code flow. The org runs on Identity Engine under the Integrator Free Plan and holds two accounts, both mine.

Access follows groups

Nobody is assigned to an app or a hostname directly. There are two role groups and four access groups, one access group per protected hostname. People are added to role groups, and group rules turn role membership into access membership. Removing someone from a role group removes every access group behind it.

Group Membership What it opens
homelab-admins Direct Every access group, through a group rule
homelab-users Direct Sign in through Cloudflare Access, plus access-home through a group rule
access-home Group rule The dashboard
access-git Group rule The Git hostname and the Forgejo login
access-files Group rule The file browser
access-photos Group rule The photos hostname and the Immich login

Two things enforce this. Okta lets a person sign in to an app only if they are in the group assigned to it. Cloudflare Access reads a groups claim in the ID token and applies one allow policy per hostname, each keyed on one access group. The claim is filtered to group names that start with access-, so the token carries what the policies need and nothing else.

This is the rule that gives admins every access group, as it stands in Terraform. The access groups come from a map, so a new hostname is one more line there. 

resource "okta_group_rule" "admins_get_all_access" {
  name              = "homelab-admins get every access group"
  status            = "ACTIVE"
  group_assignments = [for g in okta_group.access : g.id]
  expression_type   = "urn:okta:expression:1.0"
  expression_value  = "isMemberOfGroupName(\"homelab-admins\")"
  depends_on        = [okta_group.homelab_admins]
}

Signing in

The three apps share one authentication policy. Its rule requires a password plus Okta Verify, by push or by code, and asks for both again after twelve hours. The policy is assigned to the apps, so the requirement lives in one place.

Break glass. A second Cloudflare policy sits on every hostname beside the Okta one. It admits only my own email addresses through a One-time PIN, so the lab still opens if Okta is unreachable or a policy mistake locks Okta itself. Immich and Forgejo keep their local logins as well. The org has two super admins with authenticators on separate phones.

The org as code

Groups, group rules and memberships are in Terraform, so a change is a plan that is read before it is applied. The OIDC apps are the exception. Okta returns a client secret when it creates one and Terraform would keep that secret in its state file, so a script creates the apps and hands each secret to the system that needs it or to the operating system's credential store.

Nothing automated uses a shared API token. There are two OAuth service apps, each with its own private key, scopes and admin role. One manages the org for Terraform and the scripts. The other can only read it and belongs to the AI assistant. Both authenticate with private key JWT. The keys live in Windows Credential Manager and are read at run time, so no file in the repository is secret.

A read only AI assistant

Claude Code can query the org through Okta's open source MCP server, which exposes the Okta API to an AI assistant as tools. The server runs locally behind a small launcher script. Three layers keep it read only.

  • The Okta role. The assistant's service app holds the Read-only Administrator role. Okta checks the role as well as the scope, so a write scope granted by mistake would still change nothing.
  • The OAuth scopes. The token carries six read scopes. The server registers only the tools those scopes cover and checks the scope again on every call.
  • The launcher. It reads the private key from Credential Manager at launch, so no config file holds it, and it pins the server version. It passes only the tools whose names start with list_ or get_ and refuses a call to anything else. That hides one tool the server offers whatever scopes are granted, export_users_csv, which writes every user to a file. 
SCOPES = ("okta.users.read okta.groups.read okta.apps.read "
          "okta.policies.read okta.logs.read okta.deviceAssurance.read")
SERVER = "okta-mcp-server@1.1.7"


def allowed(name):
    """True for the tools a client may see: list and get tools and the scope notices."""
    return name.startswith(("list_", "get_")) or name.endswith("_scope_info")

Okta's System Log records the token grant at the start of each session and not the reads that follow. The launcher therefore logs every call it relays or refuses, with the time, the tool and the arguments, and it does not send a call that it could not log.

Limits

  • A password plus a push is MFA but it is not phishing resistant. Okta FastPass or a passkey would be.
  • Removing someone from a group takes effect at their next sign in. A Cloudflare Access session lasts up to 24 hours unless I revoke it by hand.
  • The service app that Terraform uses holds the Super Administrator role. Its token is narrowed by scopes, but the role is broader than the work needs.

The repository is private because it names my org and my hostnames. I am glad to walk through it.
