Privacy Hardening

A client-side encrypted personal drive on AWS S3, inside a minimal-trust build

My security work usually sits on the enterprise side, where the job is keeping outsiders away from an organization's data. Privacy hardening turns that around. It asks how little a single person has to hand over to the infrastructure they already depend on. This page is about one finished piece of that effort. It is a personal cloud drive where the storage provider never holds a single readable byte.

The wider build, in brief

The drive lives inside a larger minimal-trust setup spread across a few devices, each one aimed at a different threat model.

  • A privacy laptop. A ThinkPad running Linux with full disk encryption and three browser tiers that never share accounts.
  • A GrapheneOS phone that keeps its apps in isolated profiles.
  • A planned counter-surveillance radio kit, and a separate Tails appliance reserved for the highest threat model.

The rule underneath all of it is that the keys stay on my devices and the cloud is treated as storage rather than as something to trust. The rest of this page is about the drive, which is where that rule gets its cleanest expression.

Cloud durability without cloud trust

Object storage like S3 is cheap and redundant. It keeps old versions and it lives offsite. The catch is that the provider can normally read whatever you store, and so can anyone who breaches or subpoenas them. Client-side encryption removes that catch. Every file is encrypted on my laptop before it is uploaded, so S3 only ever receives ciphertext. That covers the filenames and the folder names too, not just the contents.

The secrets that make this work are an encryption password and a salt. They live only in an offline password manager. They are never uploaded and never derivable from anything that is. If the whole bucket leaked tomorrow, it would be noise.

Architecture

Two rclone remotes stacked on top of each other do the work. The lower remote talks to S3. The upper remote is an rclone crypt layer that encrypts contents and names before anything reaches it. Plaintext goes into a local folder, rclone encrypts it on the device, and the S3 layer only ever sees the encrypted objects.

Locking down the bucket

All of the provisioning here uses an administrator profile that exists only for setup. The drive itself runs as a separate least-privilege user, created further down. Substitute your own values for BUCKET_NAME, REGION, and ACCOUNT_ID. First the bucket is created and every form of public access is blocked. 

aws s3api create-bucket --bucket BUCKET_NAME --region REGION \
  --create-bucket-configuration LocationConstraint=REGION

aws s3api put-public-access-block --bucket BUCKET_NAME \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

Three more settings harden the bucket. Versioning is enabled, which keeps history and makes an accidental delete recoverable. Default server-side encryption sits underneath the client-side crypt as free defense in depth, though it is not the thing protecting the data. The client-side layer is. A lifecycle rule ages out old versions and aborts stale multipart uploads so the storage bill stays honest.

The least-privilege runtime user

The drive never runs with the admin key. It runs as a dedicated IAM user scoped to this one bucket and nothing else. 

{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "ListBucket", "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:GetBucketLocation"],
      "Resource": "arn:aws:s3:::BUCKET_NAME" },
    { "Sid": "ObjectRW", "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::BUCKET_NAME/*" }
  ]
}

The access key is printed once at creation and goes straight into the offline password manager, never to disk. Later, when that user tries to create a bucket or reach anything outside this one, AWS denies it. That denial is the point. It is proof the runtime key can do nothing but read and write objects in a single bucket.

Stacking the rclone remotes

rclone holds both remotes in its config. The lower one authenticates as the runtime user, with no_check_bucket set so it never tries to create the bucket. 

[s3raw]
type = s3
provider = AWS
region = REGION
location_constraint = REGION
server_side_encryption = AES256
env_auth = false
no_check_bucket = true
access_key_id = <RUNTIME_KEY_ID>
secret_access_key = <RUNTIME_SECRET>

The crypt remote sits on a subpath with filename and directory-name encryption, which are rclone's defaults. 

[drive]
type = crypt
remote = s3raw:BUCKET_NAME/vault
password = <obscured crypt password>
password2 = <obscured crypt salt>

rclone stores the crypt password in an obscured form, which is reversible, so the config file is sensitive. Full disk encryption protects it at rest, and rclone can add its own config password on top for a second layer.

Proof it is encrypted

This is the part worth seeing. Write a canary file, push it through the crypt remote, then look at the same object from both sides. 

echo "canary $(date)" > /tmp/canary.txt
rclone copy /tmp/canary.txt drive:      # upload through crypt

rclone cat drive:canary.txt             # prints the plaintext back
rclone ls  drive:                       # decrypted view -> "canary.txt"
rclone lsf s3raw:BUCKET_NAME/vault      # what S3 stores -> gibberish

The decrypted view shows canary.txt. The raw S3 view shows an encrypted name like mv3sk10amfki5udu75hi9cvkok. AWS only ever sees the second one.

Keeping it in sync

A systemd user timer runs a two-way sync every fifteen minutes. The sync is gated on the VPN, so it only fires when Mullvad is connected, and a guard aborts the run if more than a quarter of the files would be deleted. That guard is what stands between a bad run and a wiped drive. 

rclone bisync ~/Drive drive: --resync                          # first run only, baseline
rclone bisync ~/Drive drive: --conflict-resolve newer --max-delete 25   # routine

The phone runs Round Sync, which is rclone for Android, with the identical crypt parameters. No new secrets are created for it. The same config produces the same encrypted view, so the laptop and the phone read one drive.

What it protects, and what it does not

What it protects.

  • The contents and the filenames, from AWS and from anyone who reaches the bucket.
  • A provider breach or a subpoena, since only ciphertext is ever there.
  • Network observers, through HTTPS and the VPN.
  • Blast radius, since the runtime key reaches exactly one bucket.

What it does not.

  • Metadata. Object sizes and modification times stay visible to AWS. This is a known limit rather than a surprise.
  • A laptop that is already unlocked and compromised. Client-side encryption cannot help once the plaintext side is owned.

These edges are stated on purpose. A privacy tool that hides where it stops is worse than one that names it.

Where this leaves calendar and contacts

Files fit this model well because they sync fine as asynchronous objects. Live calendar and contacts do not, because they want a reachable server rather than an object store. So the split I settled on is files here on the encrypted S3 drive, and calendar and contacts on a separate end-to-end encrypted service.
